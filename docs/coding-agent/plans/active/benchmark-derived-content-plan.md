## Goal
- LoCoMo runs ingest the summaries and observations the official dataset provides, as provenanced memories that reach the library ingest and the precomputed-enrichment path, so the harness measures Character Memory over the full benchmark content while leaving the door open for library-generated reflections later; the lexical baseline stays a crude search over the chat log alone, the hurdle every Character Memory retrieval mechanism is compared against; LongMemEval-S ingests the 13 repeated sessions as distinct memories with their own dates, because the date changes how the graph retrieves a memory and must not be overridden (decider rulings 2026-09-14).

## Definition of Done
- LoCoMo loader: reads the official top-level `session_summary` map (keys `session_<N>_summary`, one string per session) and `observation` map (keys `session_<N>_observation`; per speaker, a list of `[statement, evidence]` pairs where evidence is a string of one or more comma-separated dialog ids, or a list of such strings); every official session parses with its summary and its typed generated observations (speaker, statement, evidence dialog ids normalized by splitting on commas and trimming); a legacy scalar entry (a bare statement string, as the existing annotation tests admit, possibly at session level with no enclosing speaker) stays an observation with no evidence and no speaker (the speaker is optional; official entries carry their enclosing map key), and an entry of any other shape is dropped and counted. The official key forms are added beside the documented bare-id and numeric lookups (the dataset admission plan committed to those for admitted record ids, with tests) in a fixed precedence, exact record id, then the official suffixed key, then the numeric fallback, with a test that pins the order when several keys are present; the crate rustdoc states every admitted key form and the order.
- LoCoMo ingest: the session summary is the episode summary and, under `index_session_summaries`, a Reflection derived memory as today; under `index_generated_observations`, each generated observation becomes one derived memory whose text is the statement alone, with provenance to the session episode and to the observations named by its normalized evidence ids that exist in the sample (an evidence id naming no turn is dropped from provenance and counted in an `unresolved_evidence_references` field on the LoCoMo memory inputs; a dropped malformed entry is counted separately in `dropped_observation_entries`; the runner's ingest progress detail reports both in every retrieval mode, including the lexical baseline, which today emits no ingest event because the event sits inside the live-adapter branch and moves out of it; the official-file test asserts both to be zero and a lexical-mode test asserts the event is emitted), and, only if ingest already emits speaker entities, attached to that entity (no new entity plumbing). The two flags keep their names and meaning: they select dataset-provided content; a library-generated source is the v0.2 comparison and is not built here.
- LoCoMo consumers: with a precomputed enrichment snapshot configured, the run ingests the dataset-derived memories and the snapshot graph together (the runner merges them in its enrichment module; external ids are disjoint by construction since dataset-derived ids carry `:derived:`; a collision is a typed failure raised by that merge boundary through an owned structured error), instead of the snapshot discarding them. The lexical baseline keeps indexing episodes and observations only (the chat log), never derived memories, by the decider's ruling: it is the crude search the Character Memory retrieval mechanisms are measured against. Because both baselines index an episode's summary text (the lexical engine directly, the vector-only mode through the live adapter over the same memory inputs), the LoCoMo memory inputs for either baseline mode carry a chat-log projection of each episode (the generic descriptive sentence used today, never the dataset summary) while the hybrid Character Memory ingest keeps the dataset summary on the episode; the engines are unchanged. Consumer-level tests prove the snapshot path carries the observations, neither baseline indexes a derived memory, and a distinctive token from a dataset summary is absent from the indexed and retrievable text of both baseline modes with the flags off.
- LoCoMo configs: `configs/locomo_retrieval.toml` indexes summaries and observations; the two baseline configs, `configs/locomo_bm25.toml` and `configs/locomo_vector.toml`, turn both flags off, since a baseline searches the chat log only (the vector-only surface policy admits episodes and observations alone, so writing derived memories there would surface nothing); the three cross-mode configs are unchanged by this plan and therefore keep the flags off; the task that next needs a cross-mode parity run must set them to match the retrieval config first, since no such run is part of this plan; no hash-cited config is edited (only continuity configs are hash-cited in the register).
- LongMemEval-S identities: ingest assigns every episode an external id that is unique within the item without narrowing admission: a session id that occurs once keeps its bare id; a later occurrence gets the bare id plus a `#<ordinal>` suffix, and if that string is itself present among the item's session ids the ordinal is raised until the id is unused. Observation ids follow their episode id. Every copy keeps its own date. The assigned identity is used only for external and provenance identities; textual content such as the episode summary sentence keeps the raw benchmark session id, so two copies with identical turns embed identically and the re-baseline measures dates, not a suffix token (regression test). One helper in the dataset crate derives the identity assignment from the item's session id list; ingest and scoring both call it, so the mapping is recomputed from the item rather than carried through the runner seam (which passes the item and the retrieved items to scoring) and nothing parses a suffix back.
- LongMemEval-S scoring: both metric families use that helper's mapping. Retrieved episode ids map to benchmark session ids; retrieved observation ids map through an exact table from assigned observation id to raw turn id that the helper produces beside the episode mapping (no delimiter parsing, since session ids are arbitrary non-blank strings) so a turn of any copy matches its bare gold turn id; after mapping, repeated ids are collapsed to their first rank so a session retrieved as two copies earns credit once and every metric stays within its bounds. Result rows keep two identity domains by contract: retrieved items carry the assigned identities (the memory that was retrieved, including which dated copy), while the gold id lists carry the raw benchmark ids; no row field is added, the README states the two domains, and a row-level regression test on a repeated-session item shows the scorer reconciling them; that test lives in a new runner integration test file owned by Task_2 (`crates/cmem-eval-runner/tests/longmemeval_repeated_sessions.rs`, service-free, driven through the lexical mode), disjoint from the runner source Task_1 owns.
- LongMemEval-S enrichment snapshots: the precomputed snapshots are built by the deterministic, provider-free source-replay builder (`scripts/enrichment/build_snapshots.py`), which today keeps only the last visible occurrence of a repeated session id and references sessions and turns by bare id. The builder applies the same identity assignment as ingest (bare id for a single occurrence, `#<ordinal>` for later ones, ordinal raised past any present id), computed over the item's full session list before the question-date visibility cutoff so it agrees with ingest even when a later raw id collides with an assigned one, and used by the builder's own validation path (its provenance lookup and cutoff selection) so the canonical generate-and-validate run passes on the regenerated artifact, with the builder's hard-coded canonical LongMemEval object counts recalculated for the retained copies and the new manifest counts recorded; the builder mirrors loader admission for repeats (identical-turn repeats are retained as distinct copies, differing-turn repeats reject the source), and its self-test fixture that asserted last-visible-wins on a differing duplicate is replaced by an identical-turn repeat with updated thread, memory and provenance expectations; every copy is represented with its own date, and thread, canonical, derived-memory and link identities all derive from the assigned session and observation identities so the copies never share a thread or a memory id, while every text field the builder writes (thread titles and summaries included) keeps the raw benchmark session id, since assigned identities serve identities only; the workflow id is part of each dataset's recipe, so the LongMemEval recipe moves to the workflow id `deterministic-exact-source-replay-v2` (assigned identities) while the LoCoMo recipe keeps `deterministic-exact-source-replay-v1`, and regeneration asserts both literals. The LongMemEval snapshot is regenerated locally by that recipe into its configured path, replacing the bare-id artifact, so every later hybrid run resolves per-copy provenance; this replacement is the task's deliberate output, not a validation side effect. Snapshot artifacts are not tracked (the datasets directory is ignored; the artifact is about 447 MiB, above what the repository host accepts), so nothing under `datasets/` is committed: the builder change is the reproducible recipe, and the regenerated artifact's manifest values (source and output SHA-256, workflow id) are recorded in this plan's Decision Log as the evidence of record. A test loads the regenerated snapshot against ingest identities and proves every reference resolves to the copy it was built from, so provenance and dates are preserved rather than rebound.
- Re-baseline: for each dataset, the lexical baseline config and the hybrid retrieval config run once at the base commit and once at the tip (same library pin, cleanup on), diffed with the runner's diff command; headline metrics, diff counts and the changed item sets are recorded in this plan's Decision Log. LongMemEval differences are confined to items among the 13.
- README's dataset and enrichment sections state both behaviours; the plan closes in completed.

## Scope / Non-goals
- Scope: `crates/cmem-eval-locomo` (types, loader, ingest, rustdoc, tests), `crates/cmem-eval-runner/src/pipeline.rs` and `crates/cmem-eval-runner/src/enrichment.rs` (snapshot merge for LoCoMo with a typed collision error, and the baseline-mode episode projection), `crates/cmem-eval-longmemeval` (ingest, scoring, types, tests), the snapshot builder's identity assignment with a local regeneration of the LongMemEval snapshot (untracked artifact; manifest values recorded), the LoCoMo benchmark configs, README, the re-baseline runs and their record.
- Non-goals: any change to the baselines' engines, selected object types or derived-memory retrieval (both baselines keep indexing episodes and observations only; the chat-log projection of their episode inputs is in scope); any LoCoMo scoring change (evidence recall stays measured on retrieved observations; whether a retrieved derived memory with evidence provenance should count is a v0.2 value-audit question, recorded below); any library change; a library-generated summary or observation source; new entity plumbing; changing the LoCoMo snapshot artifact (its ids are unaffected; regenerating it locally to prove byte-identity is validation, not a change); edits to sealed evidence or hash-cited configs; the loaders' admission rules.

## Rollback / Safety
- Reverting the branch restores today's parsing, identities and baseline inputs in code. It does not restore the replaced gitignored LongMemEval snapshot: that artifact is restored from the preserved bare-id pair while it exists, or regenerated by checking out the base commit's builder and running it against the recorded source (its manifest hash is recorded in the Decision Log), with the hash verified before any reverted hybrid run. The deliberate replacement of that ignored artifact is separate from the Git revert. Artifact schemas do not change; the values inside new run artifacts do (LongMemEval identities for repeated sessions, LoCoMo derived-memory content), which is the declared break; sealed evidence and hash-cited configs are untouched; new runs write new files only.
