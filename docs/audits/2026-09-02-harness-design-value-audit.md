## 3. The notebook core

One library crate `cmem-eval` and one binary of the same name replace the seven crates, because backend neutrality (ADR-I-0001:33) was a cost paid for mock-versus-live comparability that a pinned harness with a service-free library no longer needs.
Modules: `fixture` (schema and label validation, about 400 lines), `generator` (the scenarios, about 1,700), `driver` (scripted lifecycle and restart, about 600), `adapter` (settings, per-run store paths, external-identity registry, write through the library planner, retrieve, correct, forget, link, about 700), `embeddings` (frozen cache, controllable similarity, the generate command, about 400), `metrics` (continuity metrics, ranking metrics, token counts, about 600), `report` (aggregate, per-scenario, tuning observations, about 250), `diff` (about 150), `seal` (about 80), `cli` (about 120), plus `datasets` for the two conventional loaders and scorers (about 600) and `convert` as a second binary for the benchmark converter (about 450).
Row schema, one JSON line per query, built on the library's public types: run identity, scenario identity, query identity and text, `ExpectedRelevance` labels, `character_memory::RetrieveOutcome` (pack, telemetry, optional trace), the rendered plain context text, `Vec<character_memory::RememberOutcome>` and `Vec<character_memory::LifecycleMutationOutcome>` for the writes preceding the query, `BTreeMap<String, Option<f64>>` metrics, and latency.
Run header, one JSON file per run: harness commit, library commit, config as read plus its hash, fixture hash, store hash, embedding model and source, adapter mode (service or embedded), and generation time.
The diff tool takes two run directories, zeroes latency and identity fields, and prints per-query differences in returned identities, ranks, metrics, and degradation flags, which is the whole of tiers 1 and 2.
The seal step is one command that hashes every artifact in a run directory, writes those hashes with the header into a seal file, and copies the traces and report into a tracked evidence directory, so that a register entry cites one seal hash and a stranger can re-derive it from the tracked bytes.
Estimated size: about 6,000 to 6,500 production lines and about 2,500 test lines, against 21,300 and 13,000 today.

## 4. Migration shape

Sealed evidence that must stay readable as bytes only: reports/v0-1-5-findings-register.md; crates/cmem-eval-continuity/fixtures/continuity_v3.json and continuity_benchmarks_v1.json (register:446, 506, 549); the four committed manifest and store files under fixtures/embeddings (register:446, 507-508, 549); and the 26 hash-cited configs (register:225-240, 416-427, 523-545).
Constraint one: those files are never edited, so any config-key deletion that makes a cited config unparseable is acceptable (old artifacts are old) but a re-run of a cited config is new evidence under a new config and a new hash.
Constraint two: the frozen-store struct rejects unknown fields (frozen_embedding.rs:30), so simplifying the store means keeping its persisted fields as plain data and deleting the logic, not changing the file shape, because the committed stores cost money to regenerate.
Constraint three: no run artifact is tracked (git tracks only runs/.gitkeep and reports/.gitkeep beside the register), so the 885 MB of cited evidence under runs/ exists on one machine, including the current reference pair whose configs are themselves ignored files (register:551); the first sealing act should promote the current reference traces and report (about 2.6 MB per run) into a tracked evidence directory.

## 6. Risks of the shrink and mitigation

Risk: without the two-run gate, a tie-cohort nondeterminism like the one the register recorded (register:261-274) could go unnoticed in a tuning decision; mitigation: `diff` makes the second run a two-minute check that the sealing step requires and any tie-related library change invites.
Risk: without strict readers, a corrupted or hand-edited artifact parses silently; mitigation: the seal file's hashes catch any byte change, which is the guarantee ADR-I-0002:34 already relies on, and unsealed artifacts carry no claim.
Risk: deleting the mirror vocabulary means a library type change breaks the harness at compile time; mitigation: none needed, because a pinned harness that fails to compile against the wrong library commit is the desired behaviour and the mirror's silent-drift risk (lessons.md:346-367) disappears with it.
Risk: closeout credibility, since the register cites hashes of files only one machine holds; mitigation: promote the current reference traces and report into tracked evidence at the first seal, and leave the register text untouched with its resurrection pointer.
Risk: losing the mock loses service-free CI until the library is service-free; mitigation: order the deletion after the embedded vector-store phase, as section 4 does.
Risk: telemetry-only findings such as the root-counter omission (register:366-379) become invisible if telemetry leaves rows; mitigation: the library's telemetry type stays on every row as diagnostic data, only its promotion to metrics and per-section rates ends.
Risk: deleting sweep configs loses the ability to re-run a recorded sweep point; mitigation: the retained-defaults decision record already holds the results and the sweep plumbing stays, so any point is one new config away.
Risk: the conventional-benchmark pipelines carry no current claim and may rot; mitigation: they are named by the default-flip condition, so they are re-audited at that decision rather than deleted now.
